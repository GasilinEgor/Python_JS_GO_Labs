# Практическая работа: Разработка инструмента генерации данных для СУБД с реализацией четырёх моделей исполнения (single-thread, threading, multiprocessing, asyncio)

> **«Разработка CLI-инструмента генерации данных для реляционной СУБД с реализацией и сравнительным анализом однопоточного, многопоточного, многопроцессного и асинхронного режимов вставки»**

## Развёрнутая аннотация

**Цель работы:** получить практические навыки работы с моделями параллелизма и асинхронности в Python 3.12, научиться применять `threading`, `multiprocessing`, `asyncio` и последовательное исполнение для задач, ограниченных вводом-выводом (I/O-bound) и CPU-bound, а также освоить инструменты профилирования времени выполнения и потребления оперативной памяти.

### Стек технологий

- Python 3.12
- `threading`, `multiprocessing`, `asyncio` (стандартная библиотека)
- `psycopg` (PostgreSQL) или `sqlite3` (SQLite) — на выбор студента
- `argparse` / `click` — для CLI
- `logging` — для логирования вставок
- `psutil` / `memory_profiler` / `tracemalloc` — для замера пикового потребления памяти
- `time` / `time.perf_counter` — для замера затраченного времени
- Конфигурация через `.env` (креды БД)

## Что требуется сделать

В рамках практической работы необходимо разработать консольный инструмент (CLI) на Python 3.12, который генерирует тестовые данные и вставляет их в реляционную СУБД (PostgreSQL или SQLite). Данные генерируются **исключительно на уровне приложения** (Python), без использования серверных генераторов вроде `DEFAULT gen_random_uuid()` или `DEFAULT now()`.

Инструмент должен поддерживать **четыре режима исполнения**:

1. **`single`** — последовательное исполнение в одном потоке;
2. **`threading`** — многопоточное исполнение (`threading`);
3. **`multiprocessing`** — многопроцессное исполнение (`multiprocessing`);
4. **`asyncio`** — асинхронное исполнение (`asyncio` + асинхронный драйвер БД).

Для каждого режима необходимо логировать каждую операцию вставки (в многопоточном режиме — с указанием идентификатора потока, в многопроцессном — с указанием идентификатора процесса). В конце работы каждого режима — выводить затраченное время и пиковое потребление оперативной памяти.

По результатам необходимо оформить Markdown-отчёт с описанием всех четырёх способов запуска, командами запуска и сравнительными результатами по времени и памяти.

## Функциональные требования

### 1. Структура таблицы и схема БД

Создать таблицу со следующими столбцами:

| Столбец | Тип | Примечание |
|---------|-----|------------|
| `file_id` | UUID (PRIMARY KEY) | Генерируется **на уровне приложения**; значение должно быть одним из заранее сгенерированного пула уникальных UUID |
| `ip` | IPv4 | Генерируется на уровне приложения |
| `port` | INTEGER | Генерируется на уровне приложения |
| `added_at` | DATETIME WITHOUT TIMEZONE | Генерируется на уровне приложения (например, `datetime.utcnow()`) |

**Запрещено** использовать серверные генераторы значений (`DEFAULT gen_random_uuid()`, `DEFAULT now()`, `DEFAULT random()` и т.п.) — все значения должны формироваться в Python-коде перед вставкой.

### 2. Параметры запуска (CLI)

Инструмент должен принимать следующие параметры:

- **`--mode`** — режим исполнения: `single` | `threading` | `multiprocessing` | `asyncio` (обязательный);
- **`--db-url`** или набор `--db-host`, `--db-port`, `--db-user`, `--db-password`, `--db-name` (либо `--sqlite-path` для SQLite) — креды подключения;
- **`--workers`** — количество потоков / процессов / корутин (для `single` игнорируется);
- **`--rows`** — общее количество строк, которое нужно вставить;
- **`--unique-file-ids`** — количество уникальных `file_id`, которые будут сгенерированы заранее (пул UUID);
- **`--batch-size`** — количество строк в одной вставке (один `INSERT` может содержать несколько `VALUES`).

Параметры должны валидироваться: `batch_size` не может превышать `rows`, `unique_file_ids` должно быть ≥ 1, `workers` ≥ 1 и т.д.

### 3. Логика генерации и вставки

- **Пул `file_id`** генерируется один раз до старта вставки: `unique_file_ids` уникальных UUID. При генерации строк `file_id` выбирается случайно из этого пула (допускаются повторы, но `PRIMARY KEY` требует уникальности — во избежание конфликтов либо использовать `ON CONFLICT DO NOTHING`, либо гарантировать, что пул уникален и число строк не превышает пул; выбор стратегии — на усмотрение студента, но должен быть описан в отчёте).
- Для каждой строки генерируются `ip` (валидный IPv4), `port` (1–65535), `added_at` (`datetime` без таймзоны, близкий к текущему времени).
- Вставка выполняется **пакетами** по `batch_size` строк (multi-row `INSERT`).
- **Логирование каждой вставки**:
  - в режиме `single` — запись вида `[single] inserted batch N (size=M) at ...`;
  - в режиме `threading` — запись вида `[thread-<ident>] inserted batch N (size=M) at ...`;
  - в режиме `multiprocessing` — запись вида `[process-<pid>] inserted batch N (size=M) at ...`;
  - в режиме `asyncio` — запись вида `[task-<name>] inserted batch N (size=M) at ...`.
  - Логи должны писаться в файл и/или stdout (на усмотрение студента, но должны быть читаемы).

### 4. Ограничения по режимам

- **`single`** — один поток, один процесс, без корутин; вставки выполняются последовательно.
- **`threading`** — `workers` потоков; каждый поток получает свою долю батчей; соединение с БД — либо на поток, либо общее с блокировками (обосновать в отчёте).
- **`multiprocessing`** — `workers` процессов; **не использовать максимальное число процессов** (например, `cpu_count()`); рекомендуется `workers` ≤ 4–8. Каждый процесс создаёт собственное соединение с БД.
- **`asyncio`** — `workers` корутин; для PostgreSQL — асинхронный драйвер (`asyncpg`), для SQLite — эмуляция через `asyncio.to_thread` (обосновать в отчёте).

### 5. Замеры и вывод результатов

В конце работы каждого режима выводить в консоль:

- **Режим исполнения**;
- **Количество воркеров**;
- **Общее число вставленных строк**;
- **Затраченное время** (в секундах, с точностью до миллисекунд);
- **Пиковое потребление оперативной памяти** (в МБ) — замер через `psutil.Process().memory_info().rss` в момент пика, либо через `tracemalloc`, либо через `memory_profiler` (обосновать выбор в отчёте).

Результаты также должны сохраняться в лог-файл (например, `results.log`).

### 6. Модуль обработки ошибок и валидации

- Отдельный модуль (например, `errors.py`), содержащий:
  - описание классов исключений приложения (например, `DBConnectionError`, `InvalidParamsError`, `InsertError`);
  - единый обработчик ошибок на уровне CLI, выводящий понятное сообщение и возвращающий ненулевой код возврата.
- Валидация входных параметров — до старта вставки.

### 7. Требования к структуре проекта

- Каждый режим исполнения — отдельный модуль (например, `modes/single.py`, `modes/threading_mode.py`, `modes/multiprocessing_mode.py`, `modes/asyncio_mode.py`), реализующий единый интерфейс (например, функцию `run(...)`).
- Общие компоненты (генерация данных, логирование, замеры) — в отдельных модулях (`generator.py`, `logger.py`, `metrics.py`).
- Точка входа — `main.py` с разбором аргументов через `argparse` (или `click`).

## Перечень CLI-команд и параметров

### Точка входа

| Команда | Описание |
|---------|----------|
| `python main.py --help` | Справка по всем параметрам |
| `python main.py --mode single ...` | Последовательный режим |
| `python main.py --mode threading ...` | Многопоточный режим |
| `python main.py --mode multiprocessing ...` | Многопроцессный режим |
| `python main.py --mode asyncio ...` | Асинхронный режим |

### Параметры

| Параметр | Тип | Обязательный | Описание |
|----------|-----|--------------|----------|
| `--mode` | `single` / `threading` / `multiprocessing` / `asyncio` | да | Режим исполнения |
| `--workers` | int | для `threading` / `multiprocessing` / `asyncio` | Количество потоков/процессов/корутин |
| `--db-url` | str | да (или набор `--db-*`) | Строка подключения (например, `postgresql://...` или `sqlite:///path.db`) |
| `--rows` | int | да | Общее число вставляемых строк |
| `--unique-file-ids` | int | да | Число уникальных `file_id` в пуле |
| `--batch-size` | int | да | Строк в одном `INSERT` |
| `--log-file` | str | нет | Путь к лог-файлу (по умолчанию `insert.log`) |
| `--results-file` | str | нет | Путь к файлу с итогами (по умолчанию `results.log`) |

> Пример: `python main.py --mode threading --workers 4 --db-url postgresql://user:pass@localhost:5432/lab --rows 100000 --unique-file-ids 1000 --batch-size 500`
